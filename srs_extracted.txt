Introduction 

This document is the Software Requirements Specifications (SRS) for Dermalytics, an AI-driven skin and hair health assessment platform delivered as a responsive web application. It describes what the system must do, the interfaces it relies on, and the quality attributes it must satisfy.

Purpose of Document 

The purpose of this SRS is to define, in one place, the functional and non-functional requirements of Dermalytics version 1.0. It translates the approved project proposal into verifiable requirements and serves as the agreed baseline between the development team and the supervisor. It is the reference for design, implementation, testing and acceptance during the nine Agile sprints (September 2026 to February 2027).

Dermalytics lets users upload images of skin lesions and scalp conditions, classifies common skin conditions, estimates hair density and thinning, explains each prediction with Grad-CAM heatmaps, and stores assessment history so that users can monitor changes over time. All outputs are preliminary screening indicators, not diagnoses.

Overall System Description 

Project Background

Skin diseases and hair-related disorders such as acne, eczema, psoriasis, melanoma, dandruff, alopecia and hair thinning affect millions of people and can harm both physical health and psychological wellbeing. Early identification and continuous monitoring are important for effective treatment, yet many people, particularly in remote and underserved regions, cannot easily reach a dermatologist because of consultation costs, long waiting times and limited specialist availability.

Advances in Artificial Intelligence, Machine Learning and Computer Vision, especially Convolutional Neural Networks, have shown strong performance on medical image tasks such as skin lesion classification. Dermalytics applies these techniques in a single platform that combines skin lesion analysis and hair/scalp assessment, shows why a prediction was made through Explainable AI (Grad-CAM), and keeps a structured history of assessments. The project is developed with the Agile methodology in nine sprints.

Problem Statement

Existing dermatology applications address either skin lesions or hair loss, rarely explain their predictions, and seldom track change over time. People in underserved regions such as Karachi also struggle to access affordable early screening. Dermalytics provides one explainable, web-based platform that analyzes skin and scalp images and monitors progress.

Gaps addressed by Dermalytics:

Limited access: dermatologists are unavailable or costly in remote and underserved areas.

Fragmented tools: no single platform covers both skin and hair assessment.

Black-box AI: existing systems give predictions without explanations.

No progress tracking: users cannot monitor changes over time in a structured, model-linked way.

Project Scope

Dermalytics is an AI-powered, web-based platform for individual users seeking preliminary dermatological screening and personal health monitoring. The following functionality is in scope:

Image upload for skin and scalp analysis (camera or gallery on mobile, file picker on desktop).

Automated skin lesion classification using deep learning models, with a confidence score.

Hair density estimation and thinning detection, reported as a density score (0–100) and a thinning-stage band.

Grad-CAM explainability overlays for every prediction.

Risk flagging: low-confidence or higher-risk predictions show a “Recommend professional consultation” notice.

User accounts, historical record storage and progress tracking.

A fully responsive web interface for desktop, tablet and mobile phone screens, built as a single React.js codebase.

Platform delivery model: Dermalytics is built and deployed as one responsive web application. Once the web platform is stable, the existing web app may optionally be packaged into an installable Android APK using a WebView-based wrapper; this reuses the same front end and backend APIs and is treated as a future-scope enhancement, not a core sprint.

Not In Scope

The following are explicitly out of scope:

Real-time video analysis.

Integration with electronic health record systems.

Clinical-grade diagnosis, and prescription or treatment recommendations.

Native offline-first mobile application development (a separate native codebase with offline model inference).

Use by children, and emergency or rapidly changing presentations (for example, a bleeding or fast-growing lesion).

Project Objectives

The objective of the project is to develop an AI-powered skin and hair health assessment platform using an Agile approach that enables iterative improvement, continuous testing and user-centred feature enhancement. Specific objectives are:

Classify skin lesions automatically using deep learning models (EfficientNet, ResNet50, MobileNetV3), selecting the best backbone per task by validation accuracy and F1-score.

Assess hair health by estimating hair density and detecting signs of thinning.

Provide explainable predictions with Grad-CAM heatmaps and confidence scores to increase transparency and user trust.

Flag low-confidence or higher-risk predictions and recommend professional consultation.

Store assessment history so users can monitor changes in skin and hair health over time.

Deliver a responsive web-based interface usable on desktop and mobile browsers.

Keep the platform free to deploy in cost-sensitive settings by using an open-source technology stack.

Operating Environment

Component

Operating environment

Client

Modern web browsers on desktop/laptop, tablet and mobile phone (for example, Chrome on Android); camera or gallery access on mobile, file picker on desktop. Optional Android APK via WebView wrapper later.

Frontend

React.js with HTML5, CSS3, JavaScript and Bootstrap / Tailwind CSS, served over HTTPS.

Flask / FastAPI REST services in Docker containers; optional cloud hosting (AWS, Render or Railway).

Python with TensorFlow, PyTorch, Scikit-learn, OpenCV and Pillow. Model training on GPU (Google Colab or a local GPU); inference served by the backend.

PostgreSQL / MySQL for users, assessments and history (SQLite for prototype); file system or S3-style object storage for uploaded images and Grad-CAM outputs.

Connectivity

A standard internet-connected environment is assumed for deployment and access.

System Constraints

The system is a preliminary screening and self-monitoring aid, not a diagnostic or emergency-triage tool.

It is delivered as a web application; no separate native mobile codebase and no offline model inference.

The technology stack is open-source and free to use to minimise financial cost.

Public datasets (HAM10000, ISIC 2017 and public scalp/hair datasets) may not represent images captured in Pakistan, creating a risk of domain shift.

Model training depends on limited GPU resources (Google Colab or a local GPU).

Uploaded images and history are healthcare-related and must be stored securely with access limited to the authenticated user.

The project is limited to a team of three and to the schedule of nine sprints from September 2026 to February 2027.

Assumptions & Dependencies

Assumptions

Users have internet access and a modern browser on a desktop, laptop or mobile phone.

Users upload reasonably clear images; prediction accuracy varies with image quality, lighting and dataset diversity.

The platform is used as a supplementary screening tool and not as a replacement for professional dermatological consultation.

Assessment reports are used for periodic retraining only with the user’s explicit consent.

Dependencies

Public datasets: HAM10000, ISIC 2017 (supplementary validation) and publicly available scalp and hair datasets, supplemented by a curated, consented in-house dataset.

ImageNet-pretrained EfficientNet, ResNet50 and MobileNetV3 backbones, and the TensorFlow / PyTorch frameworks.

Google Colab or local GPU availability for model training.

Cloud hosting and storage (AWS / Render / Railway, optional) for deployment.

Partnership with a local dermatologist, only if Sprint 2 shows that external datasets do not sufficiently represent the local context.

External Interface Requirements 

Hardware Interfaces

Dermalytics does not require any dedicated or custom hardware. It interacts with the following standard hardware:

User devices (desktop, laptop, tablet, mobile phone): display, input devices, and on mobile the camera and photo gallery, used to capture or select skin and scalp images. Camera access is requested through the browser; there are no fixed physical addresses or device-specific protocols.

Server infrastructure: a standard server or cloud instance running the containerised backend and database.

Training hardware: a GPU (Google Colab or a local GPU) used offline for model training and fine-tuning; it is not part of the runtime system.

Communications Interfaces

Browser to server: all communication uses HTTPS so that data in transit is encrypted.

No dedicated LAN, wireless or device-to-device protocols are required; a standard internet connection is assumed.

Actor Action

System Response

The user has viewed a comparison of assessments over time.

Actor Action

System Response

Non - Functional Requirements 

Performance Requirements

ID

Requirement

NFR-P1

Image upload and inference shall return a result within a few seconds under normal network conditions.

NFR-P2

The interface shall remain responsive while a prediction is processing (for example, by showing progress feedback).

NFR-P3

The containerised backend shall support growth in registered users and stored assessment history without redesign.

Safety Requirements

ID

Requirement

NFR-SA1

Every skin and hair output shall be explicitly labelled as a preliminary screening indicator and not a diagnosis.

NFR-SA2

Predictions below an 80% confidence threshold, or in a higher-risk category such as suspected melanoma or basal cell carcinoma, shall display “Recommend professional consultation” rather than a standalone result.

NFR-SA3

The system shall not provide prescription or treatment recommendations, and shall state that it is not intended for children or for emergency or rapidly changing presentations.

Security Requirements

ID

Requirement

NFR-SE1

Data in transit shall be encrypted using HTTPS.

NFR-SE2

Uploaded images, Grad-CAM outputs and assessment history are healthcare-related and shall be stored securely, with access limited to the authenticated user.

NFR-SE3

The API layer shall authenticate and validate requests before routing them.

NFR-SE4

Assessment reports shall be used for model retraining only with the user’s explicit consent.

Reliability Requirements

ID

Requirement

NFR-R1

The system shall handle malformed or low-quality image uploads gracefully with a clear error message rather than failing silently.

NFR-R2

Assessment records shall be persisted so they remain available in the user’s history for later comparison.

NFR-R3

Confidence scores shall be calibrated so that the 80% flagging threshold is meaningful.

Usability Requirements

ID

Requirement

NFR-U1

The web interface shall be fully responsive, adapting layout and controls to desktop, tablet and mobile phone viewports from a single React.js codebase.

NFR-U2

Users on mobile shall be able to upload from the camera or gallery; users on desktop from a file picker.

NFR-U3

Results shall be explained in plain language, with the Grad-CAM overlay showing which regions drove the prediction.

Supportability Requirements

ID

Requirement

NFR-SU1

The codebase shall be modular, with separate model-serving, API and frontend layers so a sprint can update one layer without breaking the others.

NFR-SU2

The platform shall be deployable with Docker and shall use only open-source, free-to-use frameworks.

NFR-SU3

The system shall be verifiable through unit and integration tests (PyTest) and API tests (Postman).

NFR-SU4

The responsive web front end shall be packageable as an Android APK via a WebView wrapper without rewriting the front end or backend.

User Documentation

ID

Requirement

NFR-D1

Technical documentation and a final report shall be prepared in Sprint 9, together with a final presentation and demonstration.

NFR-D2

A short user guide describing how to take suitable photos, upload them and read the results, including the screening disclaimer, shall be provided.
